# Architecture

The patient simulator uses Twilio Programmable Voice to place every outbound call from one configured E.164 number to a destination that is hard-coded and unit-tested as `+18054398008`. When the call connects, Twilio opens a bidirectional Media Stream to a FastAPI WebSocket endpoint. The server opens a second WebSocket to OpenAI Realtime and configures the patient model with a scenario-specific private objective and realistic behavioral constraints. Both sides use G.711 μ-law (`audio/pcmu`), allowing the application to relay base64 audio payloads directly rather than add a transcoding/resampling stage. Server-side VAD controls conversational turns. OpenAI Realtime handles response interruption server-side; the bridge intentionally avoids aggressively clearing Twilio's queued outbound audio because testing showed that doing so could truncate patient speech mid-sentence.

Calls are recorded by Twilio independently of the realtime model so the final audio—not model logs—is the source of truth. A recording-status callback downloads the completed call as MP3. Post-call processing sends the recording to OpenAI's speaker-diarization transcription model and saves both machine-readable and reviewer-friendly timestamped transcripts. A separate evaluator proposes bug candidates and scores conversation quality, but candidates are intentionally not promoted automatically: the developer must listen to the recording and verify the issue before adding it to `reports/BUG_REPORT.md`. This separates low-latency conversation from slower QA analysis, keeps the live path small, and leaves auditable evidence for every reported bug.

## Key tradeoffs

I chose speech-to-speech Realtime instead of a chained STT → text LLM → TTS pipeline because the assessment explicitly prioritizes natural turn-taking, latency, interruptions, and coherent voice interaction. A chained pipeline would make intermediate text easier to inspect but would add latency and more failure boundaries during the call. I also avoided a database and production deployment stack because this is a time-boxed assessment: per-call folders provide enough traceability, while Twilio callbacks and deterministic scenario metadata keep artifacts reproducible. The system favors a small number of observable components over infrastructure that would not improve the grader's first priority: the quality of the calls.
